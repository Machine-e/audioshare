# AudioShare Bluetooth A2DP Sink 成功与排障

最后验证：2026-08-12

## 唯一支持链路

AudioShare 只支持以下 classic Bluetooth 路线：

```text
Android 媒体或音频输出
  -> classic Bluetooth A2DP
  -> Windows AudioPlaybackConnection（A2DP Sink）
  -> Windows 当前默认音频输出设备
```

Android 端提供应用内电脑列表、扫描与配对请求、收藏/最近连接和短测试音。
配对确认及媒体输出切换仍由系统完成，AudioShare 不采集手机 PCM，
也不传输或解码音频。新增的安全 RFCOMM 通道只同步电脑接收状态，不传音频。
上方日期和下方设备结论是历史 A2DP 验证；新增伴侣功能尚待双端真机验收。

## 界面与首次连接更新（2026-10-11）

- 两端右上角的外观按钮单击即可切换亮色、暗色；选择会保存在本机，首次使用默认跟随系统。
- 首页使用半透明卡片，Windows 宽窗口使用双栏，手机的连接步骤在“连接指南”中展开。
- Windows 在 `StartAsync` / `OpenAsync` 协商期间忽略临时路由事件；打开的暂时失败
  先在当前对象上尝试三次，间隔 0.5 / 1 秒；仍失败则释放对象，等待 0.5 秒后
  完整重建一次接收器，再进行有限次数打开。系统拒绝或用户取消时不继续重试。
- 连接日志保存在 `%LOCALAPPDATA%\AudioShare\connection.log`，记录进程、会话、
  启动/打开结果和重建动作，不记录设备标识或音频内容；超过 128 KiB 后重置。
- 桌面实际观察到一次启动后 `Opened` 且主题切换不关闭路由，但用户仍报告首次连接
  不可用。该观察仅证明控制路由状态，不证明有声音；首次连接问题尚未验收通过。
- 已修复主题切换时卡片颜色突变：半透明表面与背景使用同一主题插值，跟随文字渐变。
- Android 首次状态同步失败后允许在媒体连接尚未建立时进行有限次数重试。
- 这些改动经过构建和自动化测试，首次连接、持续播放及实际动画性能仍需双端真机验证。
- 已移除系统媒体音量控制及 `MODIFY_AUDIO_SETTINGS` 权限。独立传输音量尚未实现，
  音量卡片明确显示不可用。现有 A2DP 接收接口不提供 PCM 或增益处理，需要另行实现
  可处理音频样本的通路，不能只把滑块范围改为超过 100%。
- 本机只读音频会话检查发现，手机 A2DP 播放会话属于 Windows Audio 服务
  (`Audiosrv` / `svchost.exe`)，不属于 AudioShare 进程；调 AudioShare 的进程音量
  无法控制该会话，也不能据此宣称实现了应用独立增益。

## Android 更新检查（2026-10-12）

Android 底部导航分为“播放 / 设备 / 设置”：播放页选择媒体输出和查看当前电脑状态；
设备页搜索、配对、收藏电脑；设置页包含更新、桌面快捷方式、磁贴和连接排障。
状态文字旁的绿点表示已确认连接，红点表示已确认断开，黄点表示准备/同步中，
灰点表示未知。蓝牙媒体与电脑接收状态分别显示，状态通道失败不会伪装成音频断开。
页面切换保留状态订阅和设备选择，不触发断开或重连；各页分别记忆滚动位置。

- 当日发布页最新 `v0.1.0` 仅有 Windows ZIP 和校验文件，没有 Android APK；
  旧客户端把缺少固定名称 `AudioShare-Android.apk` 当作异常。
- 新检查器从最近 100 条发布中选择版本最高的正式 Android 包，跳过草稿、预发布、
  不支持的手机架构及较旧版本。支持标准包名、版本化 AudioShare 包名和 Flutter release 包名。
- 没有匹配 APK 时显示发布状态，不显示异常或声称已是最新版；网络/限流错误显示可重试提示。
- 使用 `scripts/build_android_apk.ps1` 生成 `dist/AudioShare-Android.apk`。
  本地构建不会自动上传 GitHub；发布时必须另行附上 APK，在线更新才有安装包可下载。

## 已验证环境与结论

- 手机：Xiaomi 14，HyperOS 3。
- 电脑：ASUS TUF Gaming A15 FA507UV，Windows 11。
- 蓝牙：Realtek Bluetooth Adapter，驱动 `18.4028.2506.2301`。

Xiaomi 14 已能将媒体音频稳定播放到 Windows。最初定位出的关键问题是
PowerShell 5.1 将 WinRT 对象暴露为 `System.__ComObject`，不能直接调用
`GetAwaiter()`。当前应用已不再启动 PowerShell helper，而是通过 C++/WinRT
直接枚举设备并调用 `StartAsync`、`OpenAsync`，同时在整个接收会话中保持
`AudioPlaybackConnection` 对象存活。蓝牙异步操作在后台执行，不阻塞窗口。

当前 Bluetooth-only Windows 构建已再次从应用内验证：能枚举
`Machine的Xiaomi 14`、连接返回 `Opened`，并且启动与状态事件等待期间窗口保持响应。

`waitingForRoute` 表示 Windows 接收器已就绪，但仍需在手机媒体输出中选择此电脑；
只有系统观察到真实 `Opened` 才表示媒体路由已连接，这不代表正在产生音频流量。
状态事件会在 Flutter 重挂等待器的间隙缓存。自动化状态机和 Widget 测试不能替代
真实手机、蓝牙适配器、驱动与 Windows 版本组合上的持续播放验证。

## 使用步骤

1. 手机授予“附近设备”权限，在“我的电脑”直接点击已配对电脑。
   首次使用点击 + 扫描，再点击圆形电脑卡片发起配对；双方系统确认不可跳过。
   首次发现可能需要打开 Windows 蓝牙设置使电脑可被发现，无须以手机设置为主入口。
2. 启动 AudioShare Windows 端并刷新已配对设备。
3. 选择目标手机并启动蓝牙音频接收，确认连接已启用。
4. 在 Android 的媒体输出、音频输出或播放设备选择器中选择当前 Windows PC；
   不同品牌的入口名称和位置可能不同。
5. 播放音乐；声音应从 Windows 当前默认输出设备发出。
6. 播放期间保持 AudioShare 运行，结束时在 AudioShare 中停止接收。

两端均需更新才能显示手机上的“电脑已准备好 / 连接已打开 / 连接已断开”。
状态服务不可用不等于 A2DP 不可用；按电脑界面与实际媒体输出继续排障。
Android 14+ 可请求系统媒体输出面板；12–13 从播放 App 的媒体通知选择。
系统不允许普通 App 静默强制切换全局媒体输出，不使用隐藏接口或 root 绕过。
选中电脑后可请求桌面快捷方式；快捷设置磁贴打开上次电脑，12–12L 须手动添加磁贴。

## 成功判断

- Windows 能枚举目标手机并创建 `AudioPlaybackConnection`。
- `Start` 和 `Open` 成功，连接持续保持 `Opened`。
- 手机媒体输出已明确选中 Windows PC。
- Windows 实际听到连续音频，而不只是显示“已配对”。

## 排障顺序

1. 确认运行的是最新构建，而不是 `dist` 中的历史包。
2. 在两端系统设置确认配对仍存在；必要时停止接收后重新配对。
3. 确认手机使用 classic Bluetooth 媒体配置，而不是仅有 LE 设备记录。
4. 确认 AudioShare 能枚举手机；当前版本不应启动 PowerShell，也不应再出现
   `System.__ComObject` / `GetAwaiter` 错误。
5. 区分“Windows Sink 已打开”和“手机已选择 Windows 作为媒体输出”；
   前者不会自动完成后者。
6. 确认 Windows 默认输出设备可用、音量未静音，并保持 AudioShare 运行。
7. 若连接容易掉线，检查 Windows 蓝牙服务和适配器状态，并在设备电源管理
   中关闭“允许计算机关闭此设备以节约电源”。
8. 最后再考虑更新电脑厂商提供的蓝牙驱动或测试另一只蓝牙适配器。

## Windows 已打开路由但手机提示状态不可用

0.2.1 起分别显示本机 A2DP profile 状态和电脑接收状态。状态服务不可用不等于音频断开；
profile 尚未可读也不等于未连接。系统媒体音量不能单独证明电脑接收目标。

- 两端都更新、退出旧 Windows 实例，重新开启接收；手机选中对应电脑后点“重试电脑状态”。
- `电脑状态暂不可用`：检查 Windows“手机状态同步”；手机底部消息区分 RFCOMM 建连或读取失败。
- `电脑媒体路由已打开`但目标未知：Windows 没有解析到接收目标身份；不按名字猜测。
  新版用设备接口关联属性解析真实蓝牙地址，缺失/超时保留未知，不阻断音频。
- 本机已连接而电脑明确报告停止/断开/错误：保留两项观察，检查电脑接收会话，不用本机状态覆盖错误。

0.2.2 进一步修复 SDP 注册：按微软 WinsockBluetoothConnection 示例，将分配的 RFCOMM
地址同时填入 CSADDR_INFO 的 LocalAddr 和 RemoteAddr。此前 available 只证明本地注册成功，
不证明手机能够发现正确端点。新版区分“等待状态连接”和“已发送状态帧数 / mode / target”。
帧数表示服务端发送成功，不是手机收到的确认，更不是音频统计。

手机主状态使用指定电脑的 A2DP 连接与公开 isA2dpPlaying 观测；Windows opened 只证明路由打开，
不能据此宣称正在播放。前台每 2 秒重新采样，广播最多优先 1.5 秒，后台清理，避免漏广播后旧状态永久残留。
状态服务最多自动重试 3 次，用户仍可手动重试；刷新不重新配对，也不重启音频。

## 已知限制

- 蓝牙适配器、驱动、Windows 构建和手机固件会影响兼容性。
- 蓝牙延迟、编解码质量和媒体类别路由由系统决定。
- 通话、闹钟、受保护媒体和非媒体音频可能不走 A2DP。
- 无需虚拟声卡；安装虚拟声卡不能修复 A2DP Sink 连接问题。
