## 1. 产品定位与不可破坏的边界

AudioShare 的音频链路始终是系统 classic Bluetooth A2DP：Android 作为
Source，Windows `AudioPlaybackConnection` 作为 Sink。应用不采集、编码、
上传或通过网络传输手机音频。

默认产品路线保持无网络、无麦克风、无录音、无 MediaProjection、无后台扫描。
任何未来控制通道都只能传状态和幂等控制命令，不能成为第二条音频链路。

## 2. 状态事实模型

四类事实必须在 UI 和协议中分开：

1. Android 本机事实：系统/机型、用户是否完成引导、测试音是否已开始播放。
2. 控制通道事实：是否绑定 Windows、回传是否在线、数据更新时间。
3. Windows Sink 事实：`stopped / waitingForRoute / opened / disconnected / error`。
4. 端到端音频事实：只有用户听到并确认，或未来获得可靠且可归因的音频证据，
   才能声称声音成功到达。

Windows 是 Sink 状态的唯一真相源。`opened` 只表示手机媒体路由已连接，不代表
正在产生音频、驱动健康或用户已经听到声音。禁止虚构信号百分比、延迟分、驱动
健康分或“100% connected”。

## 3. 推荐架构方向

### 当前默认：A（无权限 Android 引导层）

先做好 Android 本地向导、测试音、人工确认、排障和隐私说明；Windows 负责真实
Sink 状态、恢复操作与本地诊断。下一版不增加 Bluetooth、网络或后台权限。

### 长期结构：D（可插拔控制面）

保持 Windows 单一真相源，在其上预留可选控制面，但默认关闭。只有硬件主链路
完成回归，且用户测试证明“无法在 Android 看见 Windows 状态/远程启停”是主要
失败原因时，才进入控制面原型。

- 首选试验：前台 RFCOMM，复用 classic Bluetooth 配对；音频仍走 A2DP。
- 对照试验：BLE GATT，验证与 A2DP Sink 并行时的适配器/OEM 稳定性。
- LAN 仅作为 Bluetooth 控制面在目标矩阵持续失败、且用户通常同网时的备选，
  不作为消费版默认。
- 首个控制面原型不做后台常驻、持续扫描或自动重连。

进入控制面开发前必须满足：持续播放和断连回归完成；可用性测试证明跨设备操作
是主要痛点；原型状态更新通常低于 1 秒且不增加 A2DP 掉线；一次性 PIN/二维码
绑定、撤销和重放保护方案明确。

## 4. 串行产品里程碑

每一项必须在独立 Amp thread 中作为一个单需求完成，不并行修改 Flutter 状态、
Windows route channel、manifest 或文档热点。

### R0：真实 Sink 状态与任务式 Windows UI（代码完成，真机回归待验收）

- 严格区分 waiting、opened、disconnected。
- 事件缓存覆盖 Flutter waiter 重挂间隙。
- Windows/Android 基础任务式 UI、深色模式、窄屏和语义播报。

### R1：Android 可信连接向导与人工音频验证

- 美观的四步向导：系统配对、Windows 启动接收、手机选择 PC、播放测试音。
- 用户主动播放/停止不超过 5 秒的内置测试音，并选择“听到了/未听到”。
- 结果明确标注为用户确认；Android 不冒充检测到 Windows 状态。
- 提供设置入口和失败恢复，不新增 Bluetooth、网络、麦克风或后台权限。

### R2：Windows 一键本地诊断摘要

- 展示最后状态变化时间、用户可执行的恢复建议和最后错误。
- 一键复制 App/Windows 版本、所选设备、状态转换和脱敏错误信息。
- 诊断失败不得替换或释放正在使用的 Sink。

### R3：Windows PC 输出端点诊断

- 显示当前默认输出设备和静音状态，提供打开 Windows 声音设置。
- 明确这是 PC 输出端事实，不是手机链路质量或手机音频流量。

### R4：本地恢复便利性

- 记住上次选择的手机，提供显式“一键重试上次设备”。
- 不默认随登录自动启动，不静默抢占蓝牙媒体路由。
- 后续可加入有界会话日志和托盘状态，但保持单一 Sink 所有权。

### R5：Android 本地排障与隐私说明

- 按“找不到 PC / 一直等待 / 已连接但无声 / 经常断开”给出分支引导。
- 显示并复制必要的本机版本信息；不自动上传。
- 清楚说明系统 A2DP 音频链路和零采集/零上传边界。

### R6：可选前台控制面原型（条件里程碑）

只有满足第 3 节进入条件后才启动。Android 必须把“控制连接”“Windows Sink”
和“用户音频确认”分开展示；控制断开时 Windows 状态必须变为未知，而不能伪装成
Sink 已断开。控制功能可完全关闭，关闭后产品退回 A 路线。

## 5. 每个单需求 Thread 的固定流程

1. 阅读本 Baseline、当前代码、上一个实现 thread 和未提交状态。
2. 核实平台能力，先知只确认当前单需求 PRD、边界与验收标准。
3. PRD 明确后使用一个 `coder` subagent 实施；只有文件边界完全独立时才并行。
4. 主 agent 独立 review 状态语义、竞态、资源生命周期、权限和误导性文案。
5. 发现具体失败时使用 `debugger` subagent 修复；高风险跨模块变化再做 focused review。
6. 运行 Flutter test/analyze、受影响平台构建、原生测试及必要的界面/无障碍检查。
7. 自动化不能替代真机时，明确记录待人工验收，不能宣称通过。
8. 验证通过后形成一个本地 reviewable commit，不 push；更新本文件的完成状态。
9. 当前方案完成并稳定后，才开启下一个需求的新 thread，重复以上流程。

## 6. 全局验收红线

- Android 未经单独 PRD 不增加 Bluetooth、网络、麦克风、录音、通知监听或前台服务权限。
- 不通过隐藏 API 强制切换 Android 全局 A2DP 输出。
- 不把 `OpenAsync` 成功、设备已配对或 `Opened` 单独描述成“声音正常”。
- 任意 UI、诊断或未来控制面失败都不能关闭、复制或替换仍在使用的
  `AudioPlaybackConnection`。
- 真机矩阵至少记录设备、Android/Windows 版本、适配器/驱动、日期、waiting、
  opened、持续播放、切回手机、断开和重连结果。
